# Understand code and changes

**Second-track draft — pending course-author and independent whole-path
review.** All six modules and assessment criteria are proposed. Their inclusion
in this review site does not establish readiness or real learner success.

Start with
[shared Module 0 — GitHub for everyone](../course/00-project-and-git.md). Then
learn a small general model, try a concrete example, and apply it to an
authorized real repository. Language and framework detail comes when it helps.
Use each page for short adaptive exchanges; skip familiar explanations and
return to gaps. You do not need an implementation repository, a product brief,
the building track, or unaided coding.

## The six-module path

| Module                                                                 | Useful result                                                                                | Handoff                                                                    |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| [1. How software fits together](01-how-software-fits-together.md)      | Explain a result using code, configuration, data, dependencies, tests and a running process. | A small map and an unknown runtime fact.                                   |
| [2. Find your way through a codebase](02-find-your-way.md)             | Locate relevant files and check an agent's explanation against their contents.               | A question-led map, run/config locations and access gaps.                  |
| [3. Run and investigate software](03-run-and-investigate.md)           | Start or access a permitted environment and run one repeatable API, MCP or browser check.    | Target/version, expectation, observation, diagnostics and a next question. |
| [4. Follow a feature or change](04-follow-feature-or-change.md)        | Trace connections and explain the consequences of a proposed change.                         | A sourced path/change explanation with uncertain impact.                   |
| [5. Understand evidence of correctness](05-evidence-of-correctness.md) | Judge assertions, tested boundaries, versions and remaining gaps.                            | A bounded evidence judgment and useful next check.                         |
| [6. Read an evolving project](06-read-evolving-project.md)             | Reconcile history and runtime evidence, investigate one claim and update a dated account.    | A short project account plus a reproducible observation and limits.        |

The sequence develops reusable capabilities; it is not six long lectures or a
requirement to repeat every exercise. Existing work and equivalent understanding
can count. Each module explains what a limited result establishes and which
later question it leaves open.

## Active work, with a clear target

This is not passive code reading. Use approved agents and tools to search,
inspect, request, run QA and challenge a claim. Choose one interface relevant to
the question. Reading a command or MCP schema differs from executing it. Local
software can contact shared services; staging can hold shared data, send
messages, or incur costs. Establish the environment, version, configuration,
data and permitted effects before execution. Stop only the uncertain action and
continue with safe evidence.

Module 3 offers a downloadable fictional local API and supplied MCP/browser
alternatives. Module 5 offers a small local assertion lab; Module 6 offers
bounded fictional project history and a local API. Packet reasoning does not
prove startup, tool execution, or transfer to a real repository. Repeating a
familiar defect does not prove unfamiliar-case transfer.

## Independent application and teacher review

After a small teaching exchange, make your own prediction, map, investigation,
or assessment, optionally with an approved agent. Bring back your question,
selected repository/version, relevant excerpts, any actual commands and results,
your interpretation, and the agent's contribution. Use
[the shared review guide](../course/PRACTICE.md#bring-work-back-for-review). A
chat or repository link may be inaccessible; safe relevant excerpts work too.

The teacher credits your explanations, choices and challenges separately from
agent output. Correct generated maps or green checks alone do not prove
understanding. Missing access can leave useful partial evidence while execution
or real-repository transfer remains unassessed. Keep learner records private.
