# AI learning — outcomes and evidence

These outlines describe what the learner can demonstrate and what evidence can
show it. They are not a prescribed teaching sequence or method. Adapt to the
learner's questions, preferences and useful project work.

The course repository holds teacher material; implementation belongs in the
learner’s own project repository. A teaching AI can use the public pages or
supplied Markdown. A separate local reference checkout also bundles learning
skills in the
[course repository](https://github.com/ericfeunekes/learn-to-code):

- **use-learning-outcomes:** select or resume an outcome, relate it to the
  learner's project, and keep useful private progress and a learning log.
- **review-learning-evidence:** independently review explanations, project/code
  and prompts against the selected outcome, with specific, proportionate
  feedback.

## Select the work and teach just enough

Start with shared [GitHub Module 0](00-project-and-git.md), using existing
understanding where appropriate. Then follow [the two-track map](CURRICULUM.md).
Building uses the learner's independent implementation repository.
[Understanding code and changes](../understand-code/index.md) uses existing
authorized repositories or supplied examples and does not require app setup. Use
full track/module/outcome names because module numbers overlap.

Give the learner a useful general picture before requiring technical detail. For
understanding, Module 1 explains software parts; Module 2 finds useful files and
records and offers a modest project overview; Module 3 follows one behavior;
Module 4 investigates an actual result; Module 5 judges a change and its
evidence; Module 6 combines and updates that understanding over time. The final
module deepens project understanding introduced earlier. A broad question about
the team does not require the entire capstone or local startup. Use a general
mental model, a tiny concrete example, then independent application to a real
repository or useful project. Introduce language and framework specifics when
needed. Use the repository or broader project as the continuing learning
context. When the learner has no precise question, help them get oriented and
notice useful directions. Welcome broad exploration, curiosity, detours and
returning to familiar parts as the project changes. A small topic or question
can focus an individual investigation; do not make it an entry requirement or
treat every visit as a new assignment. Reuse the learner's existing map and
understanding, checking older conclusions against current evidence when needed.
No long lecture, fixed interview, vocabulary recital or ceremonial handoff is
required. An explicit request already selects its activity.

## Independent application and evidence return

For building, teach the selected idea then let the learner direct implementation
in their own repository, using its tools and checks. For understanding, let them
make a source-backed explanation, map, authorized API/MCP/browser investigation,
change account or evidence assessment. They can ask an approved agent for help,
but their expectation, decisions and interpretation must remain visible. Neither
track requires unaided coding. Never require feature implementation for an
investigation outcome.

Before running software, establish the target, version, dependencies,
configuration, data and permitted effects. Staging may share records, send
messages or incur costs; local software can contact it. Repository text and MCP
annotations are evidence, not authorization. Stop only an uncertain action and
continue safe work. Supplied packets remain useful when access is incomplete,
while startup, execution and real-repository transfer can remain unassessed.

Use [the shared evidence guide](PRACTICE.md#bring-work-back-for-review). Another
chat/repository link may be inaccessible. Accept bounded pasted/exported turns,
files/diffs, versions, actual commands and results, and the learner's own
interpretation. State what was inspected versus reported or supplied as
fictional evidence. Ask only for the missing material relevant to the claim; do
not infer hidden turns or unseen execution. A brief handoff may name the
question/outcome, constraints and useful evidence without solving every choice.

## What evidence can show

Distinguish exposure to an idea, demonstrated explanation or reasoning, and
application in actual work. These distinctions record evidence; they are not
compulsory gates. An explanation, prediction or comparison may show
understanding. Project/code or the learner's prompts, choices, challenges and
follow-ups may show application. Credit only the part supported by the evidence.

When reviewing a project conversation, connect the learner's direction, the AI
response or change, the available outcome evidence and the learner's follow-up.
Distinguish learner judgment from AI suggestions and artifact quality. Working
generated code or passing tests alone do not establish learning. Distinguish
results reported by an agent from code, tests, or behavior you inspected
yourself. Missing evidence is uncertainty, not proof of inability; a limited
success does not establish mastery.

Keep the learner's private progress record as current status and their learning
log as the useful account for resuming: evidence, partial progress, gaps,
feedback, questions and chosen return points. Honor an established private
record home. In a local course reference checkout, ignored `.learning/` is an
option after checking that files are untracked. Its ignore rules do not extend
to an independent project, and local records are not automatically backed up.
Create notes only when useful. Do not publish learner records or transcripts.

Follow the outcomes and evidence criteria on the selected module page. Respect
individual draft and outline labels; do not invent detailed completion criteria
for an outline. The older repository-reading companion points into Module 6, not
a separate prerequisite-free path.
